The MySQL ClickPipe provides a fully-managed and resilient way to ingest data from MySQL and MariaDB databases into ClickHouse Cloud. It supports **one-time** and **continuous ingestion** via **Change Data Capture (CDC)**.

ClickPipes can be deployed and managed using the ClickPipes UI, as well as programmatically using [OpenAPI](/integrations/clickpipes/programmatic-access/openapi) and [Terraform](/integrations/clickpipes/programmatic-access/terraform).

## Initial load {#initial-load}

[//]: # "TODO CONTENT GAP: the consistency model is still undocumented. The binlog position is recorded before the initial load starts and the snapshot doesn't run in a single transaction, so writes during the snapshot are re-delivered by CDC and deduplicated by `ReplacingMergeTree` versioning. The destination converges once CDC catches up, but the snapshot itself isn't a point-in-time cut."

[//]: # "TODO CONTENT GAP: describe when a snapshot-only pipe completes: it transitions to `Completed` once the initial load finishes, rather than going on to CDC."

Initial load is the first phase of a CDC ClickPipe, where the ClickPipe syncs the historical data of the tables in the source database over to ClickHouse, before then starting CDC. The MySQL ClickPipe parallelizes this phase automatically, which can significantly speed it up. No configuration is required.

### Parallel snapshotting {#parallel-snapshotting}

For each table, the ClickPipe picks a partition key automatically — the leading column of the primary key — and splits the table into partitions that are snapshotted in parallel. How a table is split depends on the type of the partition key column:

- **Integer and date/time columns** (`TINYINT`, `SMALLINT`, `MEDIUMINT`, `INT` and `BIGINT`, signed or unsigned, as well as `YEAR`, `DATE`, `DATETIME` and `TIMESTAMP`): the ClickPipe reads `MIN` and `MAX` for the column and divides the range into equal-width partitions, each of which becomes a `WHERE col BETWEEN start AND end` query.
- **String columns containing UUIDs** (for example a `CHAR(36)` primary key): detected automatically, with boundaries computed by treating the UUIDs as 128-bit integers and splitting the range evenly.
- **Other string columns** (slugs, emails, ULIDs or prefixed identifiers such as `user_12345`): the ClickPipe repeatedly bisects the largest remaining partition. Midpoints are interpolated and then snapped to real key values read from the table, so that boundaries respect the column's collation. Partition counts are a target rather than a guarantee here — a skewed key distribution can produce fewer or uneven partitions, but never missing or duplicated rows.

The number of partitions is derived from the table's row count as estimated by `information_schema.tables`, divided by the *Snapshot number of rows per partition* setting, and capped at 1,000 partitions per table. Because the estimate comes from table statistics rather than a `COUNT(*)` over the table, snapshots of very large tables start immediately. If the partition key column is nullable, an additional partition covers the rows where it is `NULL`.

<Note>
A table is loaded in a single thread, as one full-table `SELECT`, when it has no primary key, or when the leading column of its primary key has a type that can't be partitioned (`DECIMAL`, `TIME`, `JSON`, `ENUM`, `BINARY` and `BLOB`, geometry and vector types).
</Note>

For tables in that situation, and for tables where another indexed column has a better-distributed set of values, you can set the partition key column explicitly. The setting is available per table in the ClickPipe table picker, both when creating and when editing a ClickPipe:

<Image img="/images/integrations/data-ingestion/clickpipes/mysql/partition_key.webp" alt="Partition key column" size="md"/>

<Warning>
The partition key column must be indexed in the source table to see a good performance boost. This can be seen by running `SHOW INDEX FROM <table_name>` in MySQL.
</Warning>

### Snapshot settings {#snapshot-settings}

The following settings control how much work the initial load does in parallel:

| Setting | Default value | Description |
|---------|---------------|-------------|
| *Snapshot number of rows per partition* | 100,000 | How many rows constitute a partition, and so how many partitions a table is split into. |
| *Initial load parallelism* | 4 | How many partitions of a table are processed in parallel. Raising it speeds up the initial load, but keep it to a reasonable value for your source instance's specs to avoid overwhelming the source database. |
| *Snapshot number of tables in parallel* | 1 | How many tables are processed in parallel. This multiplies with the per-table parallelism, so with an initial load parallelism of 4 and 2 tables in parallel, the ClickPipe reads 8 partitions at a time. |

### Monitoring the initial load {#monitoring-initial-load}

You can run `SHOW PROCESSLIST` in MySQL to see the parallel snapshot in action. The ClickPipe opens multiple connections to the source database, each reading a different partition of the source table, so `SELECT` queries over different ranges mean the ClickPipe is reading the source tables. For string partition keys you will also see the short `EXPLAIN` and `LIMIT 1` probe queries used to size and place partition boundaries.

## Change Data Capture (CDC) {#cdc}

[//]: # "TODO CONTENT GAP: describe how CDC follows on from the initial load, and note that CDC-only pipes skip the initial load entirely and start from the current binlog position."

ClickPipes reads changes from the source's binary log (binlog). Unlike Postgres, there's no replication slot to manage; instead, you must configure a sufficient binlog retention period on the source.

### Replication mechanism {#replication-mechanism}

Changes are tracked by GTID by default:

<GtidRequirements />

`FilePos` replication has to be enabled for your organization by [support](https://clickhouse.com/company/contact?loc=clickpipes), and isn't available for MariaDB sources at all.

### Binlog retention {#binlog-retention}

If the ClickPipe's offset into the binlog becomes invalid — for example because the pipe was paused for longer than the retention period, or a database failover occurred while using file position replication — you need to [resync](/integrations/clickpipes/mysql/operations#resync-a-pipe) the pipe.

At the start of an initial load we record the binlog offset to start at. This offset must still be valid when the initial load finishes in order for CDC to progress. If you're ingesting a large amount of data be sure to configure an appropriate binlog retention period.

[//]: # "TODO OUTDATED: the FAQ version of the paragraph above ended by advising users to configure *Use a custom partitioning key for initial load* for large tables so a single table can be loaded in parallel. That advice is obsolete — parallel loading is now automatic for tables with a primary key, and the partition key setting is an optional override — and the UI label no longer matches, so the sentence was dropped rather than moved."

Make sure to optimize materialized views depending on destination tables, as inefficient queries can slow down ingestion to fall behind the retention period.

It's also possible for an inactive database to rotate the log file without allowing ClickPipes to progress to a more recent offset. You may need to setup a heartbeat table with regularly scheduled updates.

## Sync control {#sync-control}

This section describes how to control the sync of a MySQL ClickPipe when the ClickPipe is in **CDC (Running) mode**.

Database ClickPipes have an architecture that consists of two parallel processes - pulling from the source database and pushing to the target database. The pulling process is controlled by a sync configuration that defines how often the data should be pulled and how much data should be pulled at a time. By "at a time", we mean one batch - since the ClickPipe pulls and pushes data in batches.

There are two main ways to control the sync of a MySQL ClickPipe. The ClickPipe will start pushing when one of the below settings kicks in.

### Sync interval {#interval}

The sync interval of the pipe is the amount of time (in seconds) for which the ClickPipe will pull records from the source database. The time to push what we have to ClickHouse isn't included in this interval.

The default is **1 minute**.
Sync interval can be set to any positive integer value, but it is recommended to keep it above 10 seconds.

### Pull batch size {#batch-size}

The pull batch size is the number of records that the ClickPipe will pull from the source database in one batch. Records mean inserts, updates and deletes done on the tables that are part of the pipe.

The default is **100,000** records.
A safe maximum is 10 million.

### An exception: Long-running transactions on source {#transactions}

When a transaction is run on the source database, the ClickPipe waits until it receives the COMMIT of the transaction before it moves forward. This with **overrides** both the sync interval and the pull batch size.

### Configuring sync settings {#configuring}

You can set the sync interval and pull batch size when you create a ClickPipe or edit an existing one.
When creating a ClickPipe it will be seen in the second step of the creation wizard, as shown below:

<Image img="/images/integrations/data-ingestion/clickpipes/postgres/create_sync_settings.webp" alt="Create sync settings" size="md"/>

When editing an existing ClickPipe, you can head over to the **Settings** tab of the pipe, pause the pipe and then click on **Configure** here:

<Image img="/images/integrations/data-ingestion/clickpipes/postgres/edit_sync_button.webp" alt="Edit sync button" size="md"/>

This will open a flyout with the sync settings, where you can change the sync interval and pull batch size:

<Image img="/images/integrations/data-ingestion/clickpipes/postgres/sync_settings_edit.webp" alt="Edit sync settings" size="md"/>

### Monitoring sync control behaviour {#monitoring}

You can see how long each batch takes in the **CDC Syncs** table in the **Metrics** tab of the ClickPipe. Note that the duration here includes push time and also if there are no rows incoming, the ClickPipe waits and the wait time is also included in the duration.

## Scaling {#scaling}

<Warning>
**Most users won't need this API**

Default configuration of DB ClickPipes is designed to handle the majority of workloads out of the box. If you think your workload requires scaling, open a [support case](https://clickhouse.com/support/program) and we'll guide you through the optimal settings for the use case.
</Warning>

Scaling API may be useful for:
- Large initial loads (over 4 TB)
- Migrating a moderate amount of data as quickly as possible
- Supporting over 8 CDC ClickPipes under the same service

Before attempting to scale up, consider:
- Ensuring the source DB has sufficient available capacity
- First adjusting [initial load parallelism and partitioning](#initial-load) when creating a ClickPipe
- Checking for [long-running transactions](#transactions) on the source that could be causing CDC delays

**Increasing the scale will proportionally increase your ClickPipes compute costs.** If you're scaling up just for the initial loads, it's important to scale down after the snapshot is finished to avoid unexpected charges. For more details on pricing, see [ClickPipes pricing](/products/cloud/reference/billing/clickpipes/index).

### Prerequisites {#prerequisites}

Before you get started you will need:

1. [ClickHouse API key](/products/cloud/features/admin-features/api/openapi) with Admin permissions on the target ClickHouse Cloud service.
2. A DB ClickPipe (Postgres, MySQL or MongoDB) provisioned in the service at some point in time. CDC infrastructure gets created along with the first ClickPipe, and the scaling endpoints become available from that point onwards.

### Steps to scale DB ClickPipes {#cdc-scaling-steps}

Set the following environment variables before running any commands:

```bash
ORG_ID=<Your ClickHouse organization ID>
SERVICE_ID=<Your ClickHouse service ID>
KEY_ID=<Your ClickHouse key ID>
KEY_SECRET=<Your ClickHouse key secret>
```

Fetch the current scaling configuration (optional):

```bash
curl --silent --user $KEY_ID:$KEY_SECRET \
https://api.clickhouse.cloud/v1/organizations/$ORG_ID/services/$SERVICE_ID/clickpipesCdcScaling \
| jq

# example result:
{
  "result": {
    "replicaCpuMillicores": 2000,
    "replicaMemoryGb": 8
  },
  "requestId": "04310d9e-1126-4c03-9b05-2aa884dbecb7",
  "status": 200
}
```

### Type coercion {#type-coercion}

[//]: # "TODO Verify against DBI-378 — written from the summary recorded in this repo, because the Linear issue itself could not be read."

When a column's type is altered on the source, the destination ClickHouse column keeps the type it was created with (see [Schema changes](/integrations/clickpipes/mysql/operations#schema-changes)). Incoming values are coerced into that type:

| Incoming value | Destination column type | Coercion |
|----------------|-------------------------|----------|
| Integer | `String` | Formatted as decimal text. |
| `Float` | `Float64` | Widened. |
| `Double` | `Float32` | Narrowed, which can lose precision. |
| Text | Any numeric type | Parsed. A value that cannot be parsed, or that falls outside the range of the destination type, becomes `0`. |
| Text | `Bool` | `true` for `true`, `t`, `on`, `yes` and `1`, case-insensitively. Any other value is `false`. |

<Warning>
Coercion failures are silent: a batch that hits them logs a single warning, and the values that failed are written as `0` or `false` rather than failing the pipe. A column whose values no longer fit its destination type can therefore accumulate defaults unnoticed.
</Warning>

## Known limitations {#known-limitations}

[//]: # "TODO The three entries below were moved here from the FAQ because they describe things the MySQL ClickPipe can't do, rather than questions. There is no other existing limitations content to draw on — table and column limits, unsupported DDL, generated columns and view support are all still gaps."

### TinyInt(1) columns are ingested as Bool {#tinyint-1-as-bool}

MySQL treats `TINYINT(1)` as an alias for `BOOLEAN`, which is why the ClickPipe maps it to `Bool`. If your schema uses `TINYINT(1)` to store small integers rather than booleans, every non-zero value arrives in ClickHouse as `true`: a column holding 1, 2 and 3 lands as all 1s, and no error is raised.

The conversion happens as rows are read from MySQL, so pre-creating the destination table with an `Int8` column does not avoid it, and there is no setting to override the mapping. To preserve the values, widen the display width on the source column, for example to `TINYINT(2)`. In MySQL this is a metadata-only change, so it does not rewrite the table the way a real type change would.

### Cascading deletes aren't replicated {#support-on-delete-cascade}

Due to how MySQL [handles cascading deletes](https://dev.mysql.com/doc/refman/8.0/en/innodb-and-mysql-replication.html), they're not written to the binlog. Therefore it's not possible for ClickPipes (or any CDC tool) to replicate them. This can lead to inconsistent data. It's advised to use triggers instead for supporting cascading deletes.

### Tables with a dot in the identifier {#replicate-table-dot}

PeerDB has a limitation currently where dots in source table identifiers - aka either schema name or table name - isn't supported for replication as PeerDB can't discern, in that case, what is the schema and what is the table as it splits on dot.
Effort is being made to support input of schema and table separately to get around this limitation.

### Previously excluded columns can't be included {#include-excluded-columns}

Including columns you initially excluded from replication isn't yet supported. An alternative would be to [resync the table](/integrations/clickpipes/mysql/operations#resync-a-table) whose columns you want to include.
